# PRD-006a: First-Party Sign-In and Guided Experience - Email and Password Sign-In, Sign-Up, Forgot-Password, and Reset

> **Parent:** [PRD-006](./prd-006-first-party-sign-in-and-guided-experience-index.md)
> **Status:** Draft
> **Priority:** P0 (owner requirement 1; without it no loan officer can use the review URL)
> **Schema changes:** Additive (three new tables, twelve `security definer` functions), plus two widened check constraints on `platform.first_party_sessions` and one dropped function, each stated in D1
> **Owner Guardians:** `auth-guardian` (credential exchange, cookie, tokens, lockout), `db-guardian` (migration, definer functions, pgTAP), `security-guardian` (every definer body, the hashing module, the rate limiter, the allowlist additions), `typescript-node-guardian` (handlers and the email port), `react-guardian` (the four pages), `runbook-writing-guardian` (the seeding runbook), `email-marketing-guardian` (sending-domain checklist review)

## Goal

Give the product a real first-party login: a loan officer creates an account with a name, an email address, and a password, signs in with that email and password, clicks "Forgot your password?" when they need to, and resets it through a link sent to their inbox. The login reuses everything PRD-005b already built under the credential exchange (the session store, its functions, the cookie, CSRF, audit rows, revocation, and seeding) and replaces only the credential exchange itself: the persona selector plus operator-held shared secret from PRD-005b D4 is removed. HighLevel SSO stays out of scope; this login is the review deployment's login now and the fallback beside HighLevel SSO later.

A sign-in attempt for an unknown email has no actor and no location, so it cannot produce an audit row; D4 counts and rate-limits those attempts instead.

**External facts verified on 2026-09-19.**

- OWASP Password Storage Cheat Sheet: "If Argon2id is not available, use scrypt with a minimum CPU/memory cost parameter of (2^17), a minimum block size of 8 (1024 bytes), and a parallelization parameter of 1", with listed lower-memory alternates down to `N = 2^13` at `p = 10`; Argon2id is preferred at 19 MiB, `t = 2`, `p = 1`; a pepper "should not be stored along with the generated hash".
- Resend send endpoint: `POST https://api.resend.com/emails` with `Authorization: Bearer <key>`; required body fields `from`, `to`, `subject`; optional `html` and `text`; optional `Idempotency-Key` header (keys expire after 24 hours); success returns a JSON body with an `id`.
- MDN `Set-Cookie`: an `http:` site cannot set a `Secure` cookie, except that "the `https:` requirements are ignored when the `Secure` attribute is set by localhost"; a `__Host-` cookie "must be set with the `Secure` attribute by a secure page (HTTPS)", with no `Domain` and `Path=/`. Whether Chromium accepts a `__Host-` cookie from `http://127.0.0.1:3100` (the Playwright base URL, `playwright.config.ts:3`) is an open question for the local browser gate in PRD-006c.

## Scope

- A migration adding per-user credentials, single-use hashed tokens for password reset and email verification, and a rate-limit counter table, all unreadable by every runtime role, with twelve `security definer` functions in the PRD-005b style; the two check widenings; the drop of `platform.resolve_review_persona`.
- A password hashing and policy module in `packages/auth` on `node:crypto` scrypt with no new dependency.
- Routes and pages: sign-in, sign-up (behind a server-only switch), forgot-password, reset-password, verify-email, sign-out, and change-password.
- Per-account lockout and per-client rate limits with stated numbers.
- Generic copy that never reveals whether an email exists on the sign-in and forgot-password pages, with one deliberate exception on sign-up (D5).
- Audit rows for every account event.
- A transactional email port with a Resend adapter behind server-only environment, an honest not-configured state, and a `not sent` audit record.
- Seeding extended so the operator sets initial passwords and email addresses interactively, never through git and never printed.
- Removal of the PRD-005b D4 persona path with an exact list of what is deleted and what is kept.
- Display names for the shell (closes the gap CRR-019 records) through one more definer read.

## Design decisions

### D1. Credential store, tokens, and rate limits

One migration, `supabase/migrations/<timestamp>_password_credentials.sql`, sorting after `20260919120000`, run as `migration_owner`.

**Widen two checks, drop one function.** `platform.first_party_sessions.issued_by` gains `'password_sign_in'` and `'password_reset'`; `revocation_reason` gains `'password_changed'`. Both are pure widenings (no existing row becomes invalid) done as drop-and-recreate of the auto-named check constraints with explicit names. `platform.resolve_review_persona(uuid, text)` is dropped because its only caller is the persona route this sub-PRD deletes; leaving a pre-context definer read with no caller widens the trust boundary for nothing. `supabase/tests/first_party_sessions.pgtap.sql` loses the persona cases (lines 739-763), updates the function inventories at lines 344-345, 371, 388, and 403, and adjusts `plan(82)` at line 13.

### D2. Password hashing on `node:crypto`

`packages/auth/src/password-hash.ts`, no new dependency:

- Algorithm: scrypt from `node:crypto`, parameters `N = 2^17`, `r = 8`, `p = 1`, key length 64 bytes, 16 random salt bytes from `randomBytes`, `maxmem = 256 * 1024 * 1024`. These are the OWASP minimum for scrypt quoted above. Argon2id would be preferred by that same source, but it needs a native dependency, which the dependency policy discourages and the browser gate's no-network rule makes awkward to prove; if the pinned Node 24.18.0 exposes an Argon2 API in `node:crypto`, the implementer prefers it and records the decision (open question resolved; see Amendments, 2026-09-19).
- Cost measurement: about 390 ms per hash on the authoring workstation under Node 22.19.0. The implementer measures on the deployed runtime; if the sign-in p95 exceeds 1.5 s, the fallback is the OWASP-listed alternate `N = 2^16, r = 8, p = 2` (64 MiB), recorded as a decision, never a silent change.
- Stored format: a PHC-style string `$scrypt$ln=17,r=8,p=1$<salt base64>$<hash base64>`, so the parameters travel with the hash and can be raised later. Verification parses the stored parameters, re-derives, and compares.
- Comparison: an explicit length check first, then `crypto.timingSafeEqual` on the two derived-key buffers.
- Unknown email: the sign-in handler derives against a fixed, valid dummy PHC string so the unknown-email and wrong-password paths do the same work (005A-AC-014 style, proven by a spy).
- Rehash on sign-in: when the stored parameters differ from the current constants, a successful sign-in re-hashes the password. It must not go through `set_password`, because that revokes the user's other sessions, which a parameter upgrade does not justify. A dedicated `platform.rehash_password(user_id, password_hash)` that updates the hash and nothing else is added as a thirteenth function only when a parameter change is actually shipped; until then the constants are fixed, the rehash branch is present but unreachable, and a unit test pins the constants so a silent change fails.
- Normalization: the password is Unicode-normalized to NFC before hashing so the same visible text always hashes the same; it is never trimmed; a leading or trailing space is part of the password.
- No pepper now. The tables are unreadable by every runtime role, the hash is never logged, and a pepper adds a key-management step for the operator. A later version can add `$scrypt-p$` with an HMAC pre-step and a rehash-on-sign-in migration.

### D3. Password policy

Enforced by one module `packages/auth/src/password-policy.ts`, which also yields the user-facing reason text through PRD-006b's copy contract:

- 12 to 128 characters after NFC normalization (128 bounds the hashing input).
- No composition rules (no required digit, symbol, or case).
- Rejected when it contains the email's local part (case-insensitive, when that part is at least 4 characters) or the user's display name (case-insensitive, when at least 4 characters).
- Rejected when it appears, case-insensitively, in a bundled denylist of the most common passwords, vendored as data at `packages/auth/src/password-denylist.json` with its source and licence recorded in a header comment in the loader; the list is data, not a dependency. The implementer chooses a permissively licensed list of at least 10,000 entries and records the choice.
- The same module runs at sign-up, reset, change, and in the seeding script.

### D4. Lockout and rate limits

- Per account: 10 consecutive failures lock the account for 15 minutes (`record_password_sign_in_failure`). During lockout a correct password is still refused with the same generic response; the audit row records the lockout once. A successful sign-in or a completed reset clears the counter and the lock.
- Per client, fixed windows through `consume_auth_rate_limit`: sign-in 20 attempts per client address per 15 minutes; sign-up 10 per client address per hour; forgot-password 20 per client address per hour and 5 per email per hour (the per-email limit silently issues no token but returns the same 200 body); reset submit 10 per client address per hour; verify-email 20 per client address per hour. Over a per-address limit the route returns 429 with one generic message.
- Keys: `key_hash = HMAC-SHA256(OALO_CSRF_SERVER_SECRET, "rate-limit\0" || scope || "\0" || value)` where `value` is the client address or the normalized email. The table therefore never holds an address or an email, and rotating the CSRF secret only resets the windows. The client address is the one the platform presents; on Vercel the implementer confirms the correct forwarded-address header from Vercel's documentation before relying on it and records it (open question).
- Unknown-email sign-in attempts cannot be audited (no actor, no location); they are counted by the rate limiter and logged as a structured event with no email and no address.

### D5. Pages, routes, and responses

Pages (server-rendered, in the design system, copy from PRD-006b, quality per PRD-006d): `/sign-in`, `/sign-up`, `/forgot-password`, `/reset-password`, `/verify-email`, and `/settings/account` (change password, signed in). Routes: `POST /api/auth/sign-in`, `/api/auth/sign-up`, `/api/auth/forgot-password`, `/api/auth/reset-password`, `/api/auth/verify-email`, `/api/auth/sign-out`, `/api/auth/change-password`. Every route reads `authenticatedWorkspaceMode()` first: in `synthetic` mode the pages and routes return 404 and touch no database (the local browser suite keeps running in synthetic mode); when the mode function throws (staging or production without the review flag) they return 404; in `review` mode they serve. Nothing here decides production; that stays with the existing gates.

- **Pre-session requests** (sign-in, sign-up, forgot, reset, verify) have no session-bound CSRF token to present, so they are protected by the exact-origin and host checks from `assertBrowserMutationRequest`'s first half (the same rule PRD-005b D4 applied), by `SameSite=Lax`, and by the rate limits. A mismatched origin or host is refused with the same body as a wrong password.
- **Sign-in.** Fields: email, password, "Keep me signed in for 30 days" (unchecked by default; 12-hour lifetime otherwise, the PRD-005b value), and the visible link "Forgot your password?". Flow: rate-limit check, `lookup_password_credential(lower(btrim(email)))`, lockout check, scrypt verify (dummy derivation when no row), then on success `record_password_sign_in_success`, `list_sign_in_bindings`; with one binding, `issue_first_party_session(location, user, binding_role, application role via the shared map, hash, 43200 or 2592000, 'password_sign_in', correlation)`, then `Set-Cookie` through `serializeFirstPartySessionCookie` and `200 { next: "/overview" }`. With several bindings the response is `200 { next: "/sign-in/choose" }` where the server offers the closed list from `list_sign_in_bindings` for that user (held in a short-lived, single-use `credential_tokens`-style choice token, 5 minutes, purpose `sign_in_choice` added to the check) and the user picks one; there is no automatic highest-privilege selection, consistent with PRD-005a D3. On any failure the response is `401` with one byte-identical body and no cookie.
- **Sign-up** (only when `OALO_SELF_SERVE_SIGNUP=enabled`; otherwise page and route 404). Fields: your name, email, password (one field with a show/hide control), and an optional company or team name that becomes the location's display name (default `"<first name>'s workspace"`). Flow: rate limit, policy, hash, `register_password_account`, then the same issuance as sign-in with `issued_by 'password_sign_in'` and `200 { next: "/overview" }`; PRD-006c takes over from `/overview`. A duplicate email returns `200 { state: "existing" }` and the page shows "That email already has an account" with links to sign in and to reset. This is the one deliberate departure from non-disclosure: a sign-up page that pretends to succeed for an existing address leaves a real person with no account and no explanation, which defeats the owner's five-minute journey; the exposure is bounded by the sign-up rate limit and by the fact that sign-in and forgot-password stay fully generic. `security-guardian` ratifies at close-out. Email verification: when the email port is configured, sign-up issues a verification token (24 hours) and sends the verification email; the account signs in immediately either way and `email_verified_at` stays null until the link is used; the shell shows a dismissible notice asking the user to confirm their email only when the port is configured. Nothing is gated on verification in this sub-PRD.
- **Forgot-password.** One field, email. Always `200` with the same confirmation body and copy, whatever happened. Server side: rate limits, `lookup_password_credential`; when a row exists, `issue_credential_token(user, 'password_reset', sha256(token), 1800, correlation)` and the email; when no row exists, the same amount of token generation work with nothing persisted. The email send runs after the response is committed through Next's `after()` so response time does not depend on whether an account exists (the implementer confirms `after` on the pinned Next 16.3.3, `apps/web/package.json:21`). When the email port is not configured, the token is still issued and `auth.reset-email` is written with `result 'failed'` and subject `not_configured`; when the provider errors, `result 'failed'` and subject `provider_error`; when sent, `result 'success'` and the provider message id.
- **Reset.** The link is `${OALO_APP_URL}/reset-password?token=<43 base64url characters>`. `GET` renders the form and consumes nothing. `POST` carries the token, the new password, and its confirmation (typed twice: a typo here would lock the person out again and cost another email). On success: `consume_credential_token`, policy, hash, `set_password(user, hash, 'reset', correlation)` (which revokes every session), then a new session is issued with `issued_by 'password_reset'` and the user lands on `/overview` with a server-composed marker so the overview page renders PRD-006b D10's "Your password is saved. You're signed in." through the live region (amended 2026-09-19, see Amendments). Decision: sign the user in directly rather than send them back to the sign-in page. They have just proved control of the inbox and chosen the password; a second sign-in adds friction and a second chance to mistype for no security gain, because a compromised inbox already yields the password. An expired, consumed, superseded, or malformed token yields one generic failure state; a policy failure or mismatch leaves the token unconsumed and shows the reason. Known gap, tracked rather than closed (amended 2026-09-19, see Amendments): a person with more than one workspace goes through the sign-in-choose step after a reset, and the workspace-choice route does not carry the reset marker forward, so that person lands on `/overview` without the notice. The page carries `Referrer-Policy: no-referrer` and `Cache-Control: no-store` (set in `apps/web/src/proxy.ts` for the reset and verify paths), the token is never logged and never written to an audit row, and the existing nonce CSP is untouched.
- **Verify-email.** `GET /verify-email?token=` renders a one-button confirmation; `POST` consumes and calls `mark_email_verified`. Same header treatment as reset.
- **Sign-out.** Unchanged in behaviour from PRD-005b: requires a valid session and the full mutation gate including CSRF, calls `revoke_first_party_session(..., 'sign_out', ...)`, clears the cookie with `Max-Age=0`, and redirects to `/sign-in`.
- **Change password** (`/settings/account`). Current password, new password, confirmation. Verifies the current password, applies the policy, calls `set_password(user, hash, 'change', correlation, keep_session_id = current session)` so the current session survives and every other session is revoked.
- **Client-side storage.** No email, password, token, or session value is ever stored in `localStorage`, `sessionStorage`, or IndexedDB. Inputs carry `autocomplete="email"`, `"current-password"`, and `"new-password"` so password managers work.

### D6. Transactional email port

`apps/web/src/server/email/transactional-email.ts` defines `TransactionalEmailPort` with one method, `send(message)`, returning `{ delivered: true, providerMessageId }` or `{ delivered: false, reason: "not_configured" | "provider_error" }`. Two adapters:

- `createResendEmailAdapter({ apiKey, from, fetch })`: one `POST https://api.resend.com/emails` with `Authorization: Bearer <apiKey>`, body `{ from, to, subject, text, html }`, and an `Idempotency-Key` header equal to the token id so a retried send cannot double-deliver. Non-2xx is `provider_error`. The key never appears in a log or an error message. No `resend` package is added: the call is one `fetch`, and a dependency would add nothing but a supply-chain entry under `saveExact` and strict peers.
- `createNotConfiguredEmailAdapter()`: never calls `fetch`, always `not_configured`.

Composition: `OALO_RESEND_API_KEY` and `OALO_EMAIL_FROM` both present selects Resend; both absent selects not-configured; exactly one present is a composition failure logged by variable name, in the same shape the embedded set uses (`runtime-authentication.ts:232-253`). Synthetic mode always composes the not-configured adapter. Templates are plain text plus minimal HTML with no remote images and no tracking; copy per PRD-006b. `OALO_EMAIL_FROM` must be an address on a domain verified in Resend (the operator's ask). Email is not a G-gated provider, `tests/security/provider-side-effect-default-off.test.ts` passes unchanged, and a new test under `tests/security/` proves the not-configured adapter makes no network call and that synthetic mode never composes the Resend adapter; whether the email port should also be registered in `ProviderOperationSchema` is an open question for `security-guardian`.

## Security notes

- Passwords are hashed with scrypt at the OWASP minimum, salted per user, stored in a self-describing string, compared in constant time after a length check, and never logged. Unknown-user sign-ins derive against a dummy hash so timing does not reveal existence.
- Credential, token, and rate-limit tables have no runtime grants at all; the definer functions are the trust boundary, and `security-guardian` reviews each body for `search_path`, input validation, the absence of dynamic SQL, and the audit rows it writes.
- Reset and verification tokens are 32 random bytes, stored only as SHA-256 hashes, single-use, superseded on reissue, and short-lived (30 minutes for reset, 24 hours for verification). The reset page sends no referrer and is never cached.
- Sign-in and forgot-password never reveal whether an email exists. Sign-up reveals it deliberately, within a rate limit, for the reason D5 gives; that decision is ratified or overturned by `security-guardian` at close-out.
- Lockout is per account and time-boxed; rate limits are per keyed hash of the client address or email; neither table stores an address or an email.
- The Resend key is server-only, read once, and never included in an error. The adapter is composed only when both email variables exist; synthetic mode never composes it.
- Self-serve sign-up is off unless `OALO_SELF_SERVE_SIGNUP=enabled`, and the operator turns it on for the isolated review database deliberately. A public review URL with sign-up enabled admits real accounts into that database; that is the intended state for the review, and the database holds no customer data.
- The email address and the display name are PII. The tables say so, the retention, deletion, and export runbooks name them, and screenshots for the design review never show a real address.
- Nothing here weakens CSRF, origin, host, role-version, or expiry checks; every campaign read and write still runs under `app_runtime` with `set_app_context`.

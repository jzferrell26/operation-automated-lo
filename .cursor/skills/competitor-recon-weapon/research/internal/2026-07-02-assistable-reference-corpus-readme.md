# Assistable reference screenshots corpus README [internal worked example]

## Summary
This is the canonical corpus-organization and PII-handling precedent named directly in the Command Brief's REFERENCE MATERIAL section. It is a short README (15 lines) sitting alongside a folder tree of raw screenshot captures, and it demonstrates the minimum viable documentation a reference-screenshot corpus needs: what the screenshots are ground truth for, how they are organized, and explicit usage/PII rules. The corpus itself splits into two role-based top-level folders (`Agency Side/` and `Subaccount Side/`), each containing one subfolder per product module/surface.

## Key quotations / statistics
- "Captured 2026-07-02 by Jonathan from the live Cuantico-white-labeled Assistable account (createassistants.com). This is the pixel source of truth for the PRD-041 portal parity sweep and satisfies its reference-capture pre-task (AC-PRE.1), together with the written gap tables in `../assistable-parity-gap-analysis.md`." -- establishes provenance (who, when, from what account) and links the corpus to both a specific PRD acceptance criterion and the sibling gap-analysis document. Provenance-on-day-one is the pattern to generalize.
- "## Layout / `Agency Side/` - the agency dashboard views: Launch Pad, Subaccounts (list + detail panel), Agency, Rebilling, Integrations, Settings. / `Subaccount Side/` - the client portal views, one folder per module: Active Tags, Artifacts, Assistants (list + builder), Billing (the conditional settings tab), Calendars, Call Center, Contacts, Inbox, Integrations, Knowledge, Numbers, Observations, Settings." -- the actual folder tree observed on disk matches this description exactly (verified: `Agency Side/` has Agency, Integrations, Launch Pad, Rebilling, Settings, Subaccounts; `Subaccount Side/` has the 13 named module folders). This is the two-tier role-split-then-module-split organization pattern the Command Brief calls out to generalize.
- "Files are raw `Screenshot <date> <time>.png` captures in visual walk order within each folder." -- no renaming discipline is imposed; capture order is preserved as the implicit index. Simple, but worth flagging to weapon-forge as a minimum-viable choice, not necessarily the ideal one at scale.
- "## Usage rules / Reference for layout, spacing, states, and component anatomy when implementing PRD-041... Verify against `assistable-parity-gap-analysis.md` for the behavioral notes behind each surface. / These are competitor product screenshots held in a PRIVATE repo for internal parity work. Do not publish, embed in public docs, or ship any asset lifted from them. / Screenshots contain real client PII (names, emails, phone numbers, balances). Keep the repo private; do not paste them into external tools. / Behavior questions: check the local clone of Assistable's public docs (`C:\Users\jzfer\assistable-docs-reference`) before guessing; read facts, never copy prose." -- this is the FULL PII/usage-rules template in four sentences: (1) intended use, (2) publication/distribution restriction, (3) explicit PII acknowledgment + repo-privacy requirement + "don't paste into external tools" (a specific, actionable data-handling rule), (4) points to a separate source of truth for behavioral (non-visual) facts and repeats the read-facts-never-copy-prose rule.

## Annotations for weapon-forge
- This is short enough (15 lines) that weapon-forge can and should turn it into a literal reusable README template with placeholders, exactly as the Command Brief's IDEAS/SUGGESTIONS section requests ("The corpus README pattern... should be turned into a reusable template, not just referenced"). The four usage-rule sentences map cleanly to four template fields: {intended-use}, {distribution-restriction}, {pii-acknowledgment}, {behavioral-source-of-truth-pointer}.
- The two-tier folder structure (role-split top level, module-split second level) generalizes well to any multi-role SaaS product (e.g., admin/end-user, agency/client, org-admin/member). weapon-forge's guide should present this as "the pattern," with the Agency Side / Subaccount Side split as one instance and a note that the top-level split should mirror whatever role distinction actually exists in the target product (could be "Admin / Member," "Buyer / Seller," etc.).
- One gap worth flagging back to the user/weapon-forge rather than silently filling: this README does not document a redaction protocol for the PII it flags (it says "keep private," not "redact before committing"). The Command Brief's Critical Directive 5 goes further ("redact or exclude real customer/personal data... never commit an uncontrolled screenshot dump"), which is stricter than this precedent's actual practice. weapon-forge should treat Critical Directive 5 as the normative standard and note that this precedent corpus, if audited today, would need a redaction pass to fully comply with the Guardian's own directive -- a real, disclosed tension between precedent-as-built and directive-as-written.

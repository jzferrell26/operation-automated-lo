Encryption configuration has required `currentKeyId`, named 32-byte `keys` and an independent stable 32-byte `requestHashKey`. It has no default/environment mutation. AES-256-GCM uses fresh 12-byte nonces; AAD binds location, publication and request in a separate financing namespace. Ciphertext contains normalized minimal contact data, exact consent text/version/hash/time and immutable release/property/partner/campaign/routing attribution. Request hashes are HMAC-protected separately from the encryption key. Keep old named decryption keys until retained rows no longer need them; retain the dedupe key through encryption rotation. Tests exercise that retained-key behavior. Key-management deployment and a production keyring are not implemented or configured.

Atomic capture commits ciphertext, receipt and sanitized delivery operation in one transaction, and rechecks server-clock evidence after work before commit. Same normalized request/content returns the original unexpired receipt. Changed content conflicts. A removal/purge tombstone prevents reinsertion. New inquiries expire exactly 30 days after acceptance. Pending is not delivered; no provider claim, dispatch, reconciliation, DND mutation, field-key mapping, workflow, message or appointment is implemented by this packet.

## Migration and indexing plan

Seven additive tables separate evidence/provenance, immutable resolved sources, indexed source/evidence edges, release state, command dedupe, encrypted inquiry and sanitized delivery state. Queried identity/state/expiry/FK fields are relational columns. JSONB stores bounded whole immutable evidence/source/approval snapshots, not an unindexed queried-field escape hatch. Every new FK has a leading-column B-tree or explicit supporting index, including the nullable revoker FK. See the assigned SQL and db-weapon `guides/01-schema-design.md` (snapshots/columns) and `guides/02-indexing.md` (FK indexes).

New tables have enabled/forced RLS and private same-tenant reads. Runtime has no direct insert/update/delete grants. Mutations use finite guarded functions with empty search paths and no PUBLIC execute. Separate NOLOGIN, NOINHERIT, unprivileged database roles limit verifier admission and anonymous publication/capture; these roles have no customer UI and receive no table mutation grants. The migration grants service role membership only to its applying identity. Provision and independently qualify narrowly scoped production login membership before activation; no production app/verifier credentials were changed here. The anonymous role deliberately has no `platform.set_app_context` grant; its finite UUID/origin function resolves context, and the adapter replaces the generic context request for that role.

Lock classes: creation/RLS/triggers take ACCESS EXCLUSIVE on new empty tables; ordinary indexes take SHARE on new empty tables; FK installation takes SHARE ROW EXCLUSIVE on referenced tables. No existing table rewrite, destructive DDL, backfill, concurrent index or untracked index worker is used. Row-level evidence SHARE locks and release/operation UPDATE locks are transaction scoped. These are design statements, not measured performance findings; no EXPLAIN plan or throughput claim is supplied. See db-weapon `guides/03-migrations.md` and the migration header.

Rollback: before any activation, use a compatible binary that does not enable new writes. After first durable use retain evidence, source, releases, unexpired export/removal and sanitized audit. Roll forward with a separately assigned additive migration instead of destructive down migration. Unsupported/missing authority remains ineligible. No new report retention interval is introduced.

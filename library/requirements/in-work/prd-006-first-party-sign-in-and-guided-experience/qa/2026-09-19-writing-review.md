The same sentence already exists, unused, as `SIGN_IN.rateLimitedError` in `apps/web/src/copy/auth-messages.ts:25`, and this file's own comment says every auth sentence here is "PRD-006b D10's, split at the sentence boundary into the pair" (line 26), so the drift contradicts the module's own stated intent.

- **Recorded, not fixed:** `SIGN_IN.genericError` and `SIGN_IN.rateLimitedError` are otherwise unused (only `AUTH_CREDENTIALS_REJECTED` and `AUTH_RATE_LIMITED` actually reach the screen, through the error-code path). ### F-02. The not-connected workspace name broke mid-sentence in two places

- **Severity:** Blocker. **Status:** Fixed.
- **Where:** `apps/web/src/server/authenticated-workspace-data.ts:114` (before the fix): `REVIEW_LOCATION_DISPLAY_NAME = WORKSPACE_EYEBROW` (`"Your workspace"`, capitalized for its own use as a standalone eyebrow label).

### F-03. `RESET_PASSWORD.successNotice` is written but never shown

- **Severity:** Blocker. **Status:** Fixed (by `react-guardian`, after this review; see the fix note below).
- **Where:** `apps/web/src/copy/auth-messages.ts:75`; the gap is in `apps/web/src/features/auth/components/reset-password-form.tsx:29-39` and `apps/web/src/server/password-authentication-handler.ts:1027-1032`.
- **What was there:** D10 requires: "Success: the user lands in the workspace with the notice 'Your password is saved. You're signed in.'" The string exists, verbatim, as `RESET_PASSWORD.successNotice`. Nothing renders it. `handleResetPassword` returns `{ next: OVERVIEW_PATH }` with no signal that a reset just happened, and `ResetPasswordForm.handleSubmit` only calls `followNext(payload?.next)`, an unconditional redirect. No component reads `successNotice`, and no test asserts it appears (confirmed: it is grep-only-in-its-own-definition across `apps/web/src`).
- **Why this is a Blocker and not a Suggestion:** the person who just reset their password lands in the workspace with no confirmation their password changed or that they are now signed in. That is the honesty and trust gap D10 exists to close, not a wording nicety.
- **Why I did not fix it myself:** the fix is a behavior change (the route must signal the fresh reset, and a page must read that signal and show the notice before or as it renders), not a copy edit. My authority for this review is limited to copy modules and the string constants in the auth and guided-setup components; wiring a redirect signal into a route handler and a server-rendered page is outside that.
- **Proposed fix, concrete enough to hand to engineering:** the codebase already has this exact pattern for `SIGN_IN.signedOutNotice`: `sign-in/page.tsx` reads `parameters["signedOut"] === "1"` from the query string and the form conditionally renders the notice. The same shape closes this gap: `handleResetPassword` returns `next: \`${OVERVIEW_PATH}?passwordReset=1\`` instead of the bare path, and the authenticated layout or the overview page reads that flag once and renders `RESET_PASSWORD.successNotice` (re-exported through `apps/web/src/features/auth/strings.js` as it already is) before clearing it from the URL.
- **Fixed** by `react-guardian` on branch `worktree-wf_8189e695-0c7-1`, in the commit `fix(auth): land a completed password reset in the workspace with the saved-and-signed-in notice (PRD-006b D10, F-03)`, built exactly as proposed above:
  - `apps/web/src/server/password-authentication-handler.ts` declares `PASSWORD_RESET_NOTICE_PARAMETER`, `PASSWORD_RESET_NOTICE_VALUE`, and `OVERVIEW_AFTER_PASSWORD_RESET_PATH`, and the single-binding reset branch now returns `200 { next: "/overview?passwordReset=1" }` with the same session cookie as before. The value is composed on the server from those two constants; nothing the browser supplied is echoed, and the reset token never appears in it.
  - `apps/web/src/features/auth/components/password-reset-notice.tsx` (new) compares the query to that exact pair and renders `RESET_PASSWORD.successNotice` through `AuthNotice`, which is a `LiveRegion` at `status` urgency. A confirmation is announced without interrupting, and no sentence is written in the component.
  - `apps/web/src/app/(authenticated)/overview/page.tsx` reads `searchParams` on the server and renders the notice above the workspace heading, inside a `Stack` so the notice does not sit flush against that heading. The flag is read on the page, not in `(authenticated)/layout.tsx`, because the App Router never gives a layout the query; the page is the only server component that has it and the only one that re-renders when it changes. Because the flag lives in the query, the notice clears itself on the next navigation.
  - `apps/web/src/app/(authenticated)/review-mode-test-support.ts` (new) declares the four environment values that put the workspace into review mode, now shared by the new suite and by `overview-review-surface.integration.test.tsx`, which previously declared them itself. Extracted because the duplication gate refused the copy, and because two suites rendering "the review workspace" should not be able to drift into rendering two different ones.
- **Proven by three tests, by name.** The integration case ran green in this lane. The route-level case and the browser case both need Docker and port 3100, which another lane of this raid held for the whole ninety-minute window this lane was given, so they are written but were not executed here and `pnpm test:db` still owes a green run:
  - Route level, `pnpm test:db`: `apps/web/src/server/password-recovery-handler.postgres.test.ts`, `POST /api/auth/reset-password (006A-AC-018) > consumes the token once, revokes every session, and signs the person in`, which now asserts the exact body `{ next: "/overview?passwordReset=1" }`.
  - Integration, `pnpm test:integration`: `apps/web/src/app/(authenticated)/overview/password-reset-notice.integration.test.tsx`, `the workspace a completed password reset lands on (PRD-006b D10)`, four cases: `announces the saved-and-signed-in notice, visibly, without interrupting`, `renders for the exact address the reset route returns`, `says nothing on an ordinary visit to the workspace`, and `says nothing for a value the route never wrote`. It renders the real authenticated layout around the real overview page and asserts D10's literal inside a `role="status"` region with `aria-live="polite"`. The second case parses the route's own landing path and hands its query to the page, so a rename on either side fails rather than silently unhooking the notice.
  - Browser, the `review` project inside `pnpm test:db`: `tests/browser/review/design-quality.spec.ts`, `the workspace after a saved password meets the design quality bar`, which captures the state `reset-password--saved-notice` at all four frames in both themes and runs the same axe, overflow, target-size, and keyboard helpers as the other cases, then proves the notice is gone on the next navigation.
- **Two things this fix deliberately did not do, both for the PRD-006a owner:**
  - 006A-AC-018 still states the literal `200 { next: "/overview" }`. The shipped value is now `/overview?passwordReset=1`. The criterion's wording needs amending to match; this lane's authority did not extend to editing PRD-006a.
  - A person who holds bindings at more than one workspace resets, then passes through `/sign-in/choose`, and `POST /api/auth/choose` returns the bare `/overview`, so that path lands without the notice. Carrying the fact across the choice token is a larger change than F-03 asked for and is recorded here rather than built.
